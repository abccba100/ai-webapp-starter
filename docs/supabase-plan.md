## Supabase 연동 설계

### 1. `projects` 테이블 구조

- **테이블 목적**: 사용자가 생성하는 프로젝트(예: AI 앱, 프롬프트 세트 등)를 관리하는 최상위 엔티티.
- **주요 컬럼 (개념 설계)**  
  - **id**: 프로젝트 식별자 (UUID, 기본키).  
  - **owner_id**: 프로젝트 소유 사용자 ID (유저 테이블 `auth.users.id` 참조).  
  - **name**: 프로젝트 이름 (짧은 텍스트).  
  - **description**: 프로젝트 설명 (긴 텍스트, 선택).  
  - **status**: 프로젝트 상태 (예: `active`, `archived`, `draft`).  
  - **visibility**: 공개 범위 (예: `private`, `workspace`, `public`).  
  - **slug**: URL 식별용 슬러그(선택, 중복 불가).  
  - **config**: 프로젝트 설정(모델 선택, 온도 등의 설정을 담는 JSON 형태 필드).  
  - **created_at**: 생성 시각(읽기 전용, 기본 현재 시각).  
  - **updated_at**: 수정 시각(자동 갱신).  
  - **deleted_at**: 소프트 삭제 시각(선택, 실제 삭제 전 논리 삭제용).  

- **인덱스 / 제약 조건 (개념)**  
  - `owner_id` + `slug` 조합에 대한 유니크 제약(한 사용자가 같은 슬러그를 중복 사용 불가).  
  - `owner_id` 필수, `auth.users.id`와의 참조 무결성 유지.

### 2. `specs` 테이블 구조

- **테이블 목적**: 각 프로젝트에 속한 “사양/스펙”을 관리.  
  - 예: 프롬프트 사양, 모델 파라미터 세트, API 입·출력 형식 정의 등.

- **주요 컬럼 (개념 설계)**  
  - **id**: 스펙 식별자 (UUID, 기본키).  
  - **project_id**: 상위 프로젝트 ID (`projects.id` 참조).  
  - **title**: 스펙 제목.  
  - **summary**: 스펙 요약(선택).  
  - **type**: 스펙 유형 (예: `prompt`, `workflow`, `api_contract` 등).  
  - **version**: 버전 문자열 또는 정수(예: `1`, `2`, 또는 `v1.0.0`).  
  - **is_latest**: 해당 스펙이 프로젝트 내 최신 버전인지 여부(Boolean).  
  - **content**: 스펙 상세 내용(구조화 JSON 또는 마크다운 텍스트로 저장 가능).  
  - **metadata**: 태그, 카테고리, 사용처 등 부가 정보를 담는 JSON 필드.  
  - **created_by**: 작성자 사용자 ID (`auth.users.id` 참조).  
  - **created_at**: 생성 시각.  
  - **updated_at**: 수정 시각.  

- **인덱스 / 제약 조건 (개념)**  
  - `project_id` + `type` + `version` 조합에 대한 유니크 제약(동일 프로젝트·유형 내 버전 중복 방지).  
  - 하나의 `project_id` + `type` 조합에 대해 `is_latest = true`인 행은 최대 1개만 유지하도록 애플리케이션/트리거 레벨에서 보장.

### 3. 관계 구조

- **기본 관계**  
  - 하나의 `project`는 여러 개의 `spec`을 가질 수 있음.  
  - 관계 형태: `projects (1) — (N) specs`.  

- **참조 방향**  
  - `specs.project_id` → `projects.id` (외래 키).  
  - 삭제 전략(개념):  
    - 프로젝트 삭제 시 관련 스펙은 **소프트 삭제** 또는 **CASCADE 삭제** 중 요구사항에 따라 선택.  
    - 협업/이력 보존 필요성이 크면 `deleted_at`을 활용한 소프트 삭제를 선호.  

- **추가 확장 가능 관계** (향후 설계 고려용)  
  - 프로젝트별 협업자 관리용 `project_members` 테이블:  
    - `project_id`, `user_id`, `role`(owner, editor, viewer 등).  
  - 스펙 리뷰/코멘트용 `spec_comments` 테이블:  
    - `spec_id`, `author_id`, `body`, `created_at` 등.  

### 4. RLS(Row Level Security) 기본 전략

- **원칙**  
  - Supabase RLS는 **기본적으로 모든 테이블에서 ON**으로 두고,  
  - “명시적으로 허용된 경우에만 접근 가능”하도록 설계.  

- **`projects` 테이블 RLS 개념 정책**  
  - **읽기(SELECT)**  
    - 조건 1: `visibility = 'public'`인 프로젝트는 누구나 읽기 가능(비로그인도 허용할지 여부는 프로젝트 요구사항에 따라 결정).  
    - 조건 2: `owner_id = auth.uid()`인 행은 항상 읽기 가능.  
    - 조건 3(선택): `project_members`에 등록된 사용자(`member.user_id = auth.uid()`)도 읽기 가능.  
  - **쓰기(INSERT/UPDATE/DELETE)**  
    - INSERT: `owner_id = auth.uid()`만 허용.  
    - UPDATE/DELETE: `owner_id = auth.uid()` 또는 `project_members`에서 `role`이 `owner`/`editor`인 경우에만 허용.  

- **`specs` 테이블 RLS 개념 정책**  
  - **읽기(SELECT)**  
    - 해당 스펙이 속한 프로젝트의 RLS에 종속.  
    - 즉, `specs.project_id`에 연결된 `projects` 행을 기준으로 사용자 권한을 판정.  
  - **쓰기(INSERT/UPDATE/DELETE)**  
    - `project_id`가 가리키는 프로젝트에 대해 쓰기 권한이 있는 사용자(프로젝트 `owner` 또는 `editor`)만 허용.  

- **서비스 로직 레벨 가이드**  
  - 가능한 한 **애플리케이션 로직에서 RLS를 우회하지 않고**,  
  - 클라이언트 단에서는 **anon 키** + RLS를 통해 최소 권한만 부여.  
  - **서비스 역할 키(service_role)**는 서버 전용 환경에서만 사용하고, 브라우저/노출 영역에서는 절대 사용하지 않음.

### 5. 서버 전용 client vs 브라우저 client 사용 규칙

- **클라이언트 유형 정의**  
  - **브라우저 client**:  
    - Supabase가 제공하는 **anon 키**를 사용.  
    - RLS가 활성화된 상태에서, 로그인한 사용자(`auth.uid()`) 기준으로만 데이터에 접근.  
  - **서버 전용 client**:  
    - Supabase **service_role 키**를 사용.  
    - RLS를 우회하거나, 시스템 내부 작업(배치, 마이그레이션, 관리용 API 등)에 사용.  
    - 절대 브라우저·모바일 앱 번들에 포함되면 안 됨.

- **브라우저 client 사용 규칙**  
  - 최종 사용자 인터랙션(페이지 이동, 목록 조회, 상세 조회 등)에 대해서는 **가능한 한 브라우저 client를 사용**하여 RLS 정책을 그대로 적용.  
  - 예:  
    - 현재 로그인한 사용자의 프로젝트 리스트 조회.  
    - 특정 프로젝트 상세 및 연관 스펙 목록 조회.  
  - 장점:  
    - 서버 측 구현 최소화.  
    - RLS 규칙이 곧 보안 규칙이므로, 프론트엔드에서 직접 쿼리를 실행해도 안전.

- **서버 전용 client 사용 규칙**  
  - 다음과 같은 경우에만 서버 전용 client를 사용:  
    - **백그라운드 작업**: 주기적인 정리 작업, 마이그레이션, 통계 집계 등.  
    - **관리자/운영자 기능**: 일반 사용자 권한을 넘어서는 조회/수정(예: 모든 프로젝트 검색, 문제 되는 데이터 강제 수정).  
    - **외부 시스템 연동**: 웹훅, 큐 처리 등 인증 정보가 없는 외부 시스템에서 요청이 들어오고, 이를 서버에서 검증 후 Supabase로 위임해야 하는 경우.  
  - 서버 전용 client는 반드시 다음 조건을 지킴:  
    - 서비스 역할 키는 서버 환경 변수에만 저장.  
    - 서버 코드에서만 초기화하며, 브라우저 번들에 절대 포함되지 않도록 번들링 설정 확인.  
    - 가능한 한 RLS를 **완전히 비활성화하기보다는**, 관리용으로 꼭 필요한 최소 범위에서만 사용.

- **패턴 요약**  
  - **일반 사용자 기능**: 브라우저 client + RLS 중심.  
  - **관리/배치/백엔드 시스템 기능**: 서버 전용 client + 엄격한 환경 변수 관리.  
  - 설계 관점에서, RLS 정책이 잘 정의되어 있다면 애플리케이션 권한 체크는 “RLS → 클라이언트 레벨 보완” 순서로 생각하고, 서버 client는 예외적인 운영/관리 시나리오에만 도입.
