# Next.js 14 App Router 아키텍처 설계

이 문서는 Next.js 14 App Router 기반 프로젝트에서 레이어 분리 원칙과 서버/클라이언트 경계 규칙을 정의한다.

---

## 1. 레이어 구조 개요

| 레이어 | 경로 | 역할 | 의존 방향 |
|--------|------|------|------------|
| app | `app/` | 라우팅·레이아웃 | → features, lib |
| features | `features/` | UI + 상호작용(비즈니스 흐름) | → services, lib, types, components |
| services | `services/` | 유스케이스 로직 | → lib, types |
| lib | `lib/` | 인프라, 프로바이더, 유틸 | → types |
| types | `types/` | 도메인 모델·공통 타입 | (최하위) |
| components | `components/` | 순수 UI 컴포넌트 | → types (선택) |

- **의존 방향**: 상위 레이어만 하위 레이어를 참조한다. 하위 레이어는 상위 레이어를 알지 못한다.
- **types**는 모든 레이어에서 공통으로 사용하는 도메인·공통 타입만 둔다.

---

## 2. 레이어별 상세

### 2.1 app (라우팅 & 레이아웃)

- **경로**: `app/`
- **역할**
  - URL 기반 라우팅 (폴더 기반 라우트)
  - 레이아웃(`layout.tsx`), 로딩(`loading.tsx`), 에러(`error.tsx`), not-found 등
  - 페이지 단위 진입점만 두고, 실제 UI·로직은 features로 위임
- **규칙**
  - 페이지 컴포넌트는 가능한 한 얇게 유지
  - 데이터 페칭·인증 등은 서버 컴포넌트에서 수행 후 features에 props로 전달
  - 라우트 핸들러(`route.ts`)는 app 또는 lib의 API 래퍼만 호출

---

### 2.2 features (UI + 상호작용)

- **경로**: `features/`
- **역할**
  - 기능 단위(예: auth, dashboard, settings)로 묶인 UI와 사용자 상호작용
  - 폼 제출, 버튼 클릭, 모달 열기 등 이벤트 핸들링
  - 서버/클라이언트 구분에 맞는 컨테이너·프레젠테이션 구성
- **규칙**
  - 한 feature 폴더 안에 해당 기능에 필요한 컴포넌트·훅·상태를 함께 둠
  - 비즈니스 로직(유스케이스)은 직접 구현하지 않고 **services** 호출
  - 공통 UI 블록은 **components**에서 가져와 조합
  - 도메인 타입은 **types**에서만 import

---

### 2.3 services (유스케이스 로직)

- **경로**: `services/`
- **역할**
  - “무엇을 할지”에 해당하는 유스케이스(애플리케이션 서비스)
  - API 호출, 캐시 갱신, 도메인 규칙 조합 등
  - UI·라우팅과 무관한 순수 로직
- **규칙**
  - HTTP 클라이언트, DB 클라이언트 등은 **lib**에서 주입하거나 사용
  - 서버 전용·클라이언트 전용 서비스를 구분할 경우 폴더/파일로 분리 (예: `services/server/`, `services/client/`)
  - 타입은 **types**만 사용

---

### 2.4 lib (인프라, 프로바이더, 유틸)

- **경로**: `lib/`
- **역할**
  - 외부 연동: API 클라이언트, DB, 인증 SDK, 스토리지 등
  - React 컨텍스트·프로바이더 (테마, 인증, 라우터 등)
  - 순수 유틸 함수 (날짜, 문자열, 검증 등)
- **규칙**
  - 도메인 비즈니스 규칙은 넣지 않고, 인프라·공통 유틸만 둠
  - 서버 전용 코드는 `lib/server/`, 클라이언트 전용은 `lib/client/` 등으로 구분 가능
  - **types**만 참조

---

### 2.5 types (도메인 모델)

- **경로**: `types/`
- **역할**
  - 도메인 엔티티·값 객체·공통 DTO
  - API 요청/응답, 폼 상태 등 프로젝트 전역 타입
- **규칙**
  - 런타임 로직 없이 타입·인터페이스만 정의
  - 다른 레이어에 의존하지 않음 (가장 하위 레이어)

---

### 2.6 components (순수 UI)

- **경로**: `components/`
- **역할**
  - 재사용 가능한 순수 UI 컴포넌트 (버튼, 카드, 모달, 폼 필드 등)
  - props 기반 렌더링, 스타일·접근성에 집중
- **규칙**
  - 기능별 비즈니스 흐름·API 호출은 넣지 않음
  - 필요 시 **types**의 공통 타입만 참조
  - features에서 조합해 사용

---

## 3. 서버/클라이언트 경계 규칙

### 3.1 기본 원칙

- **기본은 서버 컴포넌트**: 새 컴포넌트는 서버 컴포넌트로 두고, 상호작용이 필요할 때만 클라이언트로 한정한다.
- **클라이언트 경계 최소화**: `"use client"`는 필요한 트리 끝단(이벤트 핸들러, 브라우저 API, 상태)에만 선언한다.
- **데이터는 서버에서**: 데이터 페칭·DB·환경 변수는 서버 컴포넌트 또는 Route Handlers에서 수행하고, 클라이언트에는 직렬화 가능한 props로만 전달한다.

### 3.2 레이어별 서버/클라이언트

| 레이어 | 서버 | 클라이언트 |
|--------|------|------------|
| **app** | `layout.tsx`, `page.tsx`, `loading.tsx`, `error.tsx`, `route.ts` | `"use client"` 페이지는 예외적으로만 |
| **features** | 데이터를 받아 렌더만 하는 컴포넌트 | 이벤트·상태·브라우저 API가 있는 컴포넌트에만 `"use client"` |
| **services** | DB·서버 전용 API → `services/server/` 또는 서버 전용 함수 | 브라우저 API·클라이언트 페칭 → `services/client/` 또는 클라이언트 전용 함수 |
| **lib** | `lib/server/`: DB, 서버 전용 SDK, 서버 유틸 | `lib/client/`: 브라우저 API, 클라이언트 SDK |
| **types** | 공통 사용 (서버/클라이언트 구분 없음) | |
| **components** | 가능하면 서버 컴포넌트로 유지 | 인터랙션 필요 시 `"use client"` 하위로 격리 |

### 3.3 데이터 흐름

- **서버 → 클라이언트**
  - 서버 컴포넌트에서 fetch/DB 결과를 props로 내려줌.
  - 직렬화 불가능한 값(함수, Symbol, 인스턴스 등)은 전달하지 않음.
- **클라이언트 → 서버**
  - Server Actions 또는 Route Handler로 요청.
  - 서버 액션은 `app/` 또는 `services/server/`에 두고, form action 또는 클라이언트에서 호출.

### 3.4 금지 사항

- 서버 전용 모듈(예: `lib/server/db`)을 클라이언트 번들에서 import하지 않기.
- `"use client"`가 있는 파일에서 서버 전용 환경 변수·비밀키에 접근하지 않기.
- 클라이언트 컴포넌트를 서버 컴포넌트의 자식으로 두되, 서버 전용 데이터는 반드시 서버 컴포넌트에서 가공한 뒤 props로만 전달하기.

---

## 4. 폴더 구조 예시 (참고)

다음은 위 원칙을 적용한 디렉터리 예시이다. 코드는 작성하지 않고 구조만 제시한다.

- `app/` — 라우트·레이아웃 (page, layout, route, loading, error)
- `features/` — 기능별 폴더 (예: `auth/`, `dashboard/`) 내부에 해당 기능의 UI·훅
- `services/` — 유스케이스 (선택: `server/`, `client/` 하위 구분)
- `lib/` — `server/`, `client/`, 유틸, 프로바이더
- `types/` — 도메인·공통 타입
- `components/` — 버튼, 카드, 폼 등 순수 UI

---

## 5. 요약

- **app**: 라우팅·레이아웃만 담당하고, 화면·로직은 features에 위임.
- **features**: UI와 상호작용을 묶고, 로직은 services, 공통 UI는 components에 의존.
- **services**: 유스케이스 로직만 두고, 인프라는 lib, 타입은 types에 의존.
- **lib**: 인프라·프로바이더·유틸, 서버/클라이언트 폴더 구분.
- **types**: 도메인·공통 타입, 다른 레이어에 의존하지 않음.
- **components**: 순수 UI, 비즈니스·API 없음.

서버/클라이언트는 “기본 서버, 필요 시만 클라이언트”로 두고, 데이터는 서버에서 페칭·가공한 뒤 props·Server Actions·Route Handler로만 주고받는다.
